File formats and data exchange

Choose the correct interchange format for mesh persistence, solver input/results and real-time browser visualization.

Abaqus and CalculiX input

The importer subset handles *NODE, mapped *ELEMENT types, explicit node/element sets and single-line GENERATE ranges. It skips comments and unrelated keyword sections. *INCLUDE, continuation connectivity records, assembly/instance transformations, nested set references, materials and analysis definitions are outside the current mesh-importer scope. The caller selects Abaqus or CalculiX importer explicitly; the shared .inp extension does not identify the dialect.

MGMB version 1.0

MGMB is a little-endian, sectioned binary container for MeshData. It uses a 64-byte header, a directory of 48-byte records and five required sections: node IDs, coordinates, element blocks, node sets and physical groups. Integers are little-endian; coordinates are IEEE-754 binary64. Strings are UTF-8 with a 32-bit byte-length prefix. Connectivity is stored as zero-based internal node indices, not external node IDs.

Version 1.0 is uncompressed and has no section checksums. Readers validate file size, offsets, bounds, counts, supported element codes, index widths and structural invariants. The format does not serialize C++ object layout, pointers, padding or ABI-dependent enum values. Use MGMB for mesh persistence; do not treat it as a corruption-proof archive.

MGWV version 1

MGWV is a render-oriented container written by WebViewWriter and read by the WebGL viewer. It consists of a 24-byte header, a padded UTF-8 JSON descriptor and a binary payload of 32-bit words. Positions are float32 and are stored relative to a bounding-box-centre origin. This improves rendering precision for models whose world coordinates are large, but MGWV is lossy and cannot round-trip a double-precision mesh.

The payload contains positions, triangle indices and per-triangle metadata, edges, optional picking identifiers, nodal fields and optional displacement or modal vectors. Field arrays use float32. Quadrilateral faces are split into two triangles for rendering; both triangles inherit the face attributes. Higher-order elements are currently rendered using corner nodes only. The file is for visualization, not numerical analysis or mesh editing.

glTF and GLB

The glTF writer exports a scene representation suitable for external viewers and rendering pipelines. It is not the authoritative store for finite-element connectivity, node sets, physical groups or result-field identity. Retain MGMB or the original solver mesh for analysis-oriented work.

Result tables

CSV/TSV imports require a column identifying external node IDs (e.g. node, node_id, nid) or external element IDs (e.g. element, eid). Suffixes _x/_y/_z form vector fields; _xx/_yy/_zz/_xy/_yz/_zx (or _xz) form recognized six-component tensors. A table is either nodal or per-element, not both. Empty cells and NaN are missing values.

Compatibility and evolution

MGMB and MGWV are explicitly versioned. A reader should reject unsupported mandatory features rather than reinterpret bytes using guessed layouts. A future incompatible binary layout requires a major version change; optional features should be represented by explicit flags or sections. For long-term reproducibility, retain source solver files and record the OpenModel version, mesh identity, solver version and unit convention alongside exported results.
